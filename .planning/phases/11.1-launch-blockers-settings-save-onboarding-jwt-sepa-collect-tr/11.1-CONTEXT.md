# Phase 11.1: Launch blockers - Context

**Gathered:** 2026-10-14
**Status:** Ready for planning

<domain>
## Phase Boundary

Close the v1.0 re-audit gaps so a new landlord can sign up, finish onboarding, configure reminders and actually collect rent by SEPA:

- NTF-05: payment follow-up settings (days, interest, templates) save and load back into Settings.
- ONB-03: after Finish/Skip onboarding the user lands on /properties without signing out and in again.
- PAY-04: SEPA collection per lease from the UI plus automatic collection ahead of the due date, with no duplicate payment rows.
- IDX-07: applying an indexation updates pending expected payments to the new rent.
- BANK-MATCHER: the OGM pass sets matchedPaymentId per bank statement row and only marks rows that actually matched.

ONB-03 and BANK-MATCHER are straight bug fixes (see audit evidence); no product decisions were needed for them.

</domain>

<decisions>
## Implementation Decisions

### Automatic SEPA collection (PAY-04)
- **D-01:** A daily job submits GoCardless payments ahead of the due date with `charge_date` = the row's due date. If the lead time is too short, GoCardless picks the earliest possible date.
- **D-02:** Lead days are configurable **per lease** (contract field), default **5**. This is a new lease column plus a field on the contract form (4 languages).
- **D-03:** Eligible leases: `paymentMethod = 'gocardless'` AND an active mandate. Bank-transfer and manual leases keep the OGM matching flow.
- **D-04:** Gocardless lease with no mandate, or a cancelled/failed mandate: skip the debit, leave the row `pending` so normal reminders apply, and notify the landlord (email and/or dashboard notice) that the mandate needs attention. Don't spam: one notice per lease per period.
- **D-05:** One row per period. Submitting a debit (automatic or manual) attaches `gocardlessPaymentId` to the existing pending expected-payment row and sets it to `processing`. `/payments/collect` must stop inserting a second row. Existing duplicate rows from earlier collect calls should be handled (planner decides cleanup).
- **D-06:** Failed debit: **one automatic retry** a few days later (planner picks the delay, respecting GoCardless retry rules). If the retry also fails, mark failed and fall back to the normal late-payment reminders and landlord late-payment email. The manual retry button (PAY-05) stays available.
- **D-07:** Scheduling follows the existing timezone rules (resolveTimezone / getScheduleTimezone, BullMQ cron with tz).

### Manual collect button (PAY-04)
- **D-08:** "Collect via SEPA" is a row action in the payments list, on pending/failed rows of gocardless leases with an active mandate. It collects exactly that row.
- **D-09:** Amount is the row's amount (rent + charges), fixed. No custom amounts.
- **D-10:** Allowed even when the automatic run would pick the row up later: a manual submit sets the row to `processing`, the auto-run only picks `pending` rows, so no double debit. Rows already `processing` do not show the button.
- **D-11:** Confirm dialog before submitting, showing tenant, amount and expected charge date. Result shown as a toast.

### Reminder templates (NTF-05)
- **D-12:** Custom templates are stored **per language** (en/nl/fr/de) and per level (friendly/formal/final). The current flat friendly/formal/final columns are not enough, so a schema change is needed. Keep the Settings page's per-language editor; the API schema must match what the page sends.
- **D-13:** Fallback: a missing or blank override uses the built-in default (`DEFAULT_EMAIL_TEMPLATES`) in the tenant's language. Saving must not require every field (drop the min(1)-on-everything validation).
- **D-14:** The Settings page GETs `/settings/payment-follow-up` and shows the stored values (days, interest, templates). Days and interest save independently of templates.
- **D-15:** SMS/WhatsApp text is in scope: Settings also gets SMS templates per language and level (fallback `DEFAULT_SMS_TEMPLATES`), and the reminder channel path (reminderChannel / sendReminderViaPreferredChannel) uses the landlord's custom SMS text. Also fix the language fallback mismatch (due-date SMS falls back to 'nl', others to 'en'): use one consistent fallback.
- **D-16:** "Reset to default" per template, which clears the override.

### Indexation and pending rows (IDX-07)
- **D-17:** The indexation apply dialog asks "new rent from" (start month). Default = next due period. The landlord may pick an earlier month back to the lease anniversary. For **residential** leases at most 3 months before today (Belgian rule: back-indexation limited to 3 months before the written request). For **commercial** leases back to the anniversary, no 3-month cap.
- **D-18:** All `pending` rows due on or after the chosen start month get the new rent (rent part updated, charges unchanged).
- **D-19:** Rows in that range that are already `paid` stay untouched. The summed difference goes into **one extra pending row** ("Indexation catch-up"), due on the next payment date. It must be collectable by SEPA and matchable like any other row.
- **D-20:** Rows already submitted to GoCardless (`processing`) in the range: cancel the GoCardless payment if it can still be cancelled and resubmit at the new amount. If it can no longer be cancelled, fold the shortfall into the catch-up row.
- **D-21:** No tenant notification from this change; the existing indexation letter flow covers that.

### Claude's Discretion
- Retry delay for D-06, cleanup approach for existing duplicate rows, landlord notice channel details for D-04.
- ONB-03 approach (JWT `trigger: 'update'` handling plus `useSession().update()`, or re-reading the DB flag), as long as Finish/Skip lands on /properties in one go.
- BANK-MATCHER implementation details.
- Schema shape for per-language templates (JSON column vs child table). Note the Drizzle baseline is stale: use `db:push` or hand-written DDL, not `db:generate`.

</decisions>

<specifics>
## Specific Ideas

- The user expects "pick start month" to follow Belgian law and the landlord's choice, not a hardcoded rule.
- All verification happens in production (pre-release), on m1.
- Dates in UI as dd/mm/yyyy via formatDate(); all new UI text in EN/NL/FR/DE.

</specifics>
