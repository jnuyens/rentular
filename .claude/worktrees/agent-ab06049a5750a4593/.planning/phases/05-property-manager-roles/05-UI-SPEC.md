## Typography

| Role | Size | Weight | Line Height | Tailwind Class |
|------|------|--------|-------------|----------------|
| Body | 14px | 400 (regular) | 1.5 | `text-sm` |
| Label / UI emphasis | 14px | 600 (semibold) | 1.5 | `text-sm font-semibold` |
| Subheading | 18px | 600 (semibold) | 1.3 | `text-lg font-semibold` |
| Heading | 24px | 600 (semibold) | 1.2 | `text-2xl font-semibold` |

**Weights declared: 2** -- 400 (regular) and 600 (semibold).

All emphasis previously split across `font-medium` (500) and `font-bold` (700) in this phase collapses to `font-semibold` (600). This applies to: page headings, subheadings, form labels, button text, badge text, and table headers. The existing codebase uses `font-bold` on page headings and `font-medium` on form labels/buttons, but this phase's new components will standardize on the 2-weight contract. Existing components outside this phase's scope are not affected.

**Source:** Codebase audit of `apps/web/app/(dashboard)` pages. Dominant weights are 400 (body text) and 600 (subheadings, badges, table headers). Headings use 700 and labels use 500 in some existing pages, but this phase normalizes to 2 weights for design consistency.

## Interaction Contracts

### 1. Invite Property Manager Flow

**Trigger:** Owner/co-owner clicks "Invite Manager" button on property managers page.

**Modal contents:**
- Email input (required, type="email")
- Role select: dropdown with options `co_owner`, `manager`, `accountant`, `viewer` (not `owner`)
- Property select: multi-select of owned properties (pre-selected if inviting from a specific property context)
- Submit button: "Send Invitation"
- Dismiss button: "Discard Invitation"

**States:**
| State | Behavior |
|-------|----------|
| Default | Form fields empty, Submit enabled |
| Submitting | Submit button shows "..." and is disabled, form inputs disabled |
| Success | Modal closes, manager list refreshes, no toast (consistent with existing pattern) |
| Error | Red error banner inside modal: `rounded-lg bg-red-50 px-4 py-3 text-sm text-red-700` |
| Duplicate | API returns 409, error message: "This user already has access to the selected property." |

### 2. Invitation Accept/Decline Flow

**URL:** `/invite/accept?token={uuid}`

**States:**
| State | Behavior |
|-------|----------|
| Valid token, logged in | Show invitation details (property name, role, who invited). Two buttons: "Accept Invitation" (primary) and "Decline" (secondary outline). |
| Valid token, not logged in | Redirect to `/login?returnUrl=/invite/accept?token={uuid}`. After login, redirect back. |
| Expired token | Show error: "This invitation has expired. Please ask the property owner to send a new invitation." with link to dashboard. |
| Invalid/used token | Show error: "This invitation link is no longer valid." with link to dashboard. |
| Accept success | Redirect to `/properties` dashboard. |
| Decline success | Show confirmation: "Invitation declined." with link to dashboard. |

### 3. Role Badge on Property Cards

**Placement:** Below the property type badge row, same line as existing type/heating badges.

**Behavior:**
- Owner's own properties: Show `Owner` badge in blue
- Managed properties: Show role badge (e.g., `Manager`) in corresponding color
- Badge is always visible, not interactive (no click action)

### 4. Sidebar Role Filtering (D-09)

**Behavior:** Navigation items are conditionally rendered based on the user's most permissive role across all their accessible properties.

| Nav Item | Minimum Role Required |
|----------|----------------------|
| Properties | viewer |
| Tenants | viewer (hidden for accountant) |
| Leases | viewer (hidden for accountant) |
| Payments | viewer |
| Indexation | viewer (hidden for accountant) |
| Communications | viewer |
| Maintenance | viewer (hidden for accountant) |
| Settings | owner only (actual account owner, not co_owner) |

**Note:** If a user has mixed roles (e.g., co_owner on property A, viewer on property B), show the maximum set of nav items available to them. The per-property permission enforcement happens at the API level.

### 5. Revoke Access Flow

**Trigger:** Owner/co-owner clicks "Revoke" button on a manager row.

**Confirmation:** Browser `window.confirm()` dialog (consistent with existing delete pattern in properties page -- no custom modal for destructive actions in current codebase).

**Confirmation text:** "Remove {name}'s access to {property}? This takes effect immediately."

**After revoke:** Row removed from manager list. Email notification sent to the revoked user (backend, not UI-visible).

### 6. Change Role Flow

**Trigger:** Owner/co-owner clicks the role dropdown on a manager row.

**Behavior:** Inline `<select>` element with available roles. On change, immediately PATCHes the API. No separate save button.

**States:**
| State | Behavior |
|-------|----------|
| Updating | Select disabled momentarily |
| Success | New role reflected in badge and dropdown |
| Error | Revert dropdown to previous value, show inline error text |

## Accessibility Contracts

| Element | Requirement |
|---------|-------------|
| Role badge | Use `<span>` with visible text. No ARIA role needed (decorative label with visible text). |
| Role select dropdown | Standard `<select>` element. Labeled with `<label>` element via `htmlFor`. |
| Invite modal | Focus trapped inside modal when open. `Escape` key closes modal. `aria-modal="true"` on dialog container. |
| Revoke confirmation | `window.confirm()` is natively accessible. |
| Invitation accept page | Primary action (Accept) has `autofocus` attribute. |
| Sidebar nav filtering | Hidden items are removed from DOM, not visually hidden. Screen readers see only permitted items. |
| Status badges (Pending) | Color is not the only indicator. Text label "Pending" is always present alongside any color coding. |

- Role badges: Inline `rounded-full` pills that wrap naturally in flex containers
